================================================================================
CHANDRA — END-TO-END WORKFLOW
Client-Facing Architecture & Data Flow Reference
================================================================================

This document explains, in plain language, what happens from the moment a user
opens the Chandra console to the moment an AWS remediation action finishes
running — including where the LLM is allowed to act, where humans are gated
in, and what each component does.


--------------------------------------------------------------------------------
1. WHAT IS CHANDRA?
--------------------------------------------------------------------------------

Chandra is an AI Cloud Engineer that takes a user's operational goals
(Key Result Areas, or KRAs), inspects an AWS account end-to-end, recommends
concrete remediation actions, and — under human supervision — executes those
actions safely inside a sandbox.

The product is built on three layers:

  1. A Next.js operations console (the UI the user sees)
  2. A FastAPI backend service (HTTP/WS surface, async job tracking)
  3. A set of "digital worker" agents built on LangGraph + Amazon Bedrock


--------------------------------------------------------------------------------
2. THE HIGH-LEVEL FLOW (ONE PICTURE)
--------------------------------------------------------------------------------

  ┌──────────────────────────────────────────────────────────────────────────┐
  │ 1. USER  ───  defines KRAs (predefined + custom)                         │
  │                                                                          │
  │ 2. FRONTEND  ───  posts KRAs + region to FastAPI                         │
  │                                                                          │
  │ 3. FASTAPI  ───  hands the request to the Observation Agent              │
  │                                                                          │
  │ 4. OBSERVATION  ───  11 AWS tools run in parallel → structured report    │
  │       │            (KRA status, issues, cost snapshot, actions[])        │
  │       ▼                                                                  │
  │ 5. ANALYZER  ───  LLM scores each action (severity / priority /          │

  │       ▼                                                                  │
  │ 6. EXECUTION AGENT  ───  LLM writes Terraform/code → validates →         │

--------------------------------------------------------------------------------
3. STAGE 1 — USER ONBOARDING (FRONTEND)
--------------------------------------------------------------------------------

The user lands on the app and walks through a 5-step wizard.

  Step 1: Agent identity     — name, avatar, role, maturity level
  Step 2: KRAs (Key Results) — pick from a catalog of predefined KRAs and/or
                               type in CUSTOM KRAs (e.g. "create s3 bucket in
                               us-east-1" or "deploy EC2 with Terraform")
  Step 3: Permissions        — choose what the agent is allowed to do
  Step 4: Review             — see the configured profile
  Step 5: Deploy             — finish onboarding, enter the dashboard

  Where the data lives:
    - Browser:  sessionStorage + localStorage (instant restore on refresh)
    - Backend:  customKras.json on disk (custom KRA library persists across
               users and sessions)

  Files involved:
    frontend/app/onboarding/page.tsx          — hosts the wizard
    frontend/components/OnboardingWizard.tsx  — 5-step flow, all form logic
    frontend/store/OnboardingContext.tsx      — shared state, debounced save
    frontend/store/kraCatalog.ts              — predefined KRA definitions
    customKras.json                           — backend KRA persistence

  Once the wizard is complete, the user is routed to the dashboard
  (frontend/app/dashboard/page.tsx).

--------------------------------------------------------------------------------

  3 seconds and renders:

  Key files:
    digitalworker_agents/aws_execution_agent.py     — the full state machine
    tools/jira_tools/create_jira_ticket.py          — adds summary comment
    iac/reference/                                  — code-style reference
                                                      templates

  Key safety properties:
    • All shell commands run with timeout (default 500s)
    • Cancellation is cooperative (SIGKILL / taskkill /F on cancel)
    • The agent remembers past errors via agent_memory.json and avoids
      repeating them in future runs
    • Mid-run HITL fires if the agent is "stuck" on the same error class
    • When the budget (default 6 iterations) is exhausted, the job halts

7. ASYNCHRONOUS JOB PATTERN (HOW THE UI STAYS RESPONSIVE)
--------------------------------------------------------------------------------

Every long-running backend operation is a job:

  Submit   POST /getAgentObservations      → 202 { job_id, poll_url }
  Submit   POST /analyzeActions            → 202 { job_id, poll_url }
  Submit   POST /orchestrate               → 202 { job_id, poll_url }
  Poll     GET  /jobs/status/{job_id}      → { status, progress, message,
                                                  result | error }
  Stop     POST /orchestrate/stop/{job_id} → 200 { status: "stopped" }
  Logs     GET  /orchestrate/logs/{job_id} → text file
  Sandbox  GET  /download_sandbox?path=…   → .zip of generated artifacts
  Destroy  POST /destroy_sandbox           → terraform destroy + Jira note

  Why this matters:
    • The UI never blocks. The user can leave the page and come back.
    • Multiple actions can run in parallel.
    • Every job has a unique thread_id, so re-attaching mid-run is possible.

8. HUMAN-IN-THE-LOOP (HITL) GATES
--------------------------------------------------------------------------------

Chandra is "supervised autonomy" — it never mutates AWS without a human
willing it to. There are FOUR HITL touchpoints:

  (a) OBSERVATION → ANALYZER GATE
      The user must click "Approve" on the action list before
      /analyzeActions is even called.

  (b) ANALYZER → EXECUTION GATE
      Each action in the analyzer output carries a humanReviewNeeded
      boolean. The frontend only enables "Run" for actions marked
      humanReviewNeeded=false unless the user explicitly overrides
      (via "Approve & Run"). The action's Jira ticket captures this
      audit trail.

  (c) PRE-EXECUTION (interrupted inside the Execution Agent)
      If the Execution Agent's `analyze` step decides it needs
      clarification (e.g. "which VPC?"), it raises an `interrupt()`.
      The graph halts, the user's frontend sees
      "awaiting_input" + a list of questions, and the user submits
      answers via the same orchestrate endpoint. The graph resumes
      where it left off.

  (d) MID-RUN HITL (stuck loop)
      If the agent hits STUCK_THRESHOLD consecutive identical errors,
      it raises an interrupt with the failing error text. The user
      can provide guidance (e.g. "use a different AMI") and the agent
      resumes with that context.

  Persistence:
    • All approval state, escalation payloads, and audit receipts
      persist to PostgreSQL via SQLAlchemy + Alembic
      (src/chandra/db/models.py)
    • Every orchestration run writes logs/<job_id>.log
    • Cross-run memory: agent_memory.json (rolling log of 50 runs)

10. DATA SCHEMAS THAT FLOW THROUGH THE SYSTEM
--------------------------------------------------------------------------------

  KRAInput          { code?: KRA-XX, name?, description }
                    Sent: frontend → /getAgentObservations
                    Used by: Observation Agent to scope its report

  ObservabilityReport (output of Stage 2)
                    { health, kra_status[], issues[],
                      observations[], cost_snapshot[],
                      security_posture[], compliance_summary,
                      actions[]: ActionItem }
                    ActionItem: { actionName, actionDescription,
                                  service, kraCode, priorityLevel,
                                  steps[] }
                    Sent back: Stage 2 → frontend dashboard

  ActionResult      (output of Stage 3)
                    { actionName, severity, humanReviewNeeded,
                      jiraIssueKey, jiraUrl, priority }
                    Sent back: Stage 3 → frontend approval cards

  ActionInput       (sent to /orchestrate)
                    { actionName, actionDescription, service,
                      kraCode, priorityLevel, steps[] }
                    Drives: Stage 4 (Execution Agent)

  PipelineResponse  (output of Stage 4)
                    { statusCode, status, thread_id,
                      sandbox_path, iterations_used,
                      iterations[IterationRecord],
                      execution_results[ExecutionResult],
                      summary }
                    Sent back: Stage 4 → frontend execution card

  EscalationPayload { finding_id, resource_id, severity,
                      service, region, summary,
                      recommended_action }
                    Used by: SNS publisher when a HIGH-severity
                             action needs human eyes

12. WHAT THE CLIENT SEES AT EACH STAGE
--------------------------------------------------------------------------------

  Stage 1 — Onboarding
    • 5-step wizard with animated transitions
    • KRA library persists across sessions
    • Custom KRA = "name + description" (free-form)

  Stage 2 — Observation
    • Animated progress while job runs
    • "Live ops event stream" populates as issues come in
    • KRA scorecard tiles (Green / Yellow / Red, %)
    • Cost snapshot cards (daily spend, 24h delta)
    • Issues table with P1/P2/P3 badges
    • Action queue with per-action "Approve" buttons

  Stage 3 — Analyzer
    • Action cards now show:
        - Severity (HIGH / MEDIUM / LOW)
        - Human Review badge
        - Jira issue key + link
    • "Run" button enabled per action

  Stage 4 — Execution
    • Per-action execution card with:
        - Live status (pending → running → completed)
        - Real-time log stream (auto-scrolling)
        - Stop / Cancel button
        - Download artifacts (.zip)
        - Destroy (terraform destroy + Jira note)
    • Mid-run "questions" panel if agent needs clarification

  Always-on
    • Audit trail in Postgres (runs, findings, briefings, escalations)
    • Cross-run memory in agent_memory.json
    • Bedrock token usage + cost tracked per run
    • Eval harness scores pipeline vs Terraform-seeded ground truth

13. SAFETY GUARDRAILS (NON-NEGOTIABLE)
--------------------------------------------------------------------------------

  1. LLM never invents findings.    Detectors produce data; LLM ranks.
  2. LLM never invents cloud IDs.   Generator must use `data` sources or
                                     pre-fetched account context.
  3. Sandbox isolation.             subprocess is killed on stop; sandbox
                                     zip is downloadable but isolated.
  4. Every boto3 call paginated.    No silent truncation.
  5. Every AWS client via factory.  No raw `boto3.client(...)`.
  6. Postgres writes only in `persist`
     and in Alembic migrations.     One node owns all DB writes.
  7. Read-only by default.          Writes are gated by approval + dry-run.
  8. Circuit breakers.              Validate retries capped at 3, plan
                                     review retries capped at 2, total
                                     orchestration iterations capped at 6.
  9. Cancellation cooperative.      User stop = immediate subprocess kill.
 10. Decisions in `decision_router`,
     `action_executor`, and
     `escalation` are DETERMINISTIC.
                                     LLM is not allowed in these nodes.
