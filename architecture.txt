SECTION 1: CURRENT CHANDRA ARCHITECTURE
────────────────────────────────────────────────────────────────────────────────

PURPOSE
-------
Read-only autonomous AWS observation agent. Detects misconfigurations and
health issues across five KRAs, ranks them using an LLM, and produces a
scored briefing report. It NEVER mutates infrastructure.

SECTION 2: PROPOSED DIGITAL WORKER PLATFORM ARCHITECTURE

PURPOSE
-------
Autonomous, self-healing Digital Worker that takes Job Descriptions (JDs) and
KRAs, discovers current cloud state, generates missing IaC/scripts, executes
them safely inside a sandbox, validates KRA completion against the live
environment, and produces a full audit ledger. HITL gating prevents runaway
execution on high-risk operations.


ZONE BREAKDOWN
--------------

  Zone 1: Control Plane        — UI, FastAPI, job queue, state DB
  Zone 2: Agent Runtime        — The cognitive brain (7 agents)
  Zone 3: Isolated Sandbox     — Ephemeral execution environment

INFRASTRUCTURE GUARDRAILS
--------------------------

  1. State Dehydration    Entire agent memory serialized to Postgres before
                          HITL wait. Celery worker terminates. Webhook from
                          UI re-hydrates and resumes the graph.

  2. Stateless Sandbox    Generator + Executor have zero host shell access.
                          Only /tmp/workspace/ volume is accessible.
                          Container destroyed after each execution.

  3. Circuit Breakers     Both loops cap at max_retries=3. Breach →
                          row flagged FAILED_AUTOMATION, terminal logs
                          escalated to HITL UI.

  4. Audit Ledger         Every agent hand-off, approval, execution log,
                          and reconciliation attempt persisted to Postgres
                          and surfaced in the HITL UI.

SHORT ANSWER
------------
Partially — but not as-is. The current architecture provides a solid, working
foundation for the Observation layer. The execution, generation, HITL, and
reconciliation layers are entirely absent and must be purpose-built.

  5 KRA detector suite           Becomes the Observability Agent's discovery
                                 engine directly. No rewrite needed.

  LangGraph pipeline skeleton    The graph topology (fanout + merge + serial

                                 new nodes (Planner, Generator, Executor,
                                 Validation) rather than replacing it.

  Bedrock / LLM integration      The ChatBedrockConverse setup in composer.py

  Pydantic schemas (briefing/)   The schema discipline is already in place.

WHAT IS MISSING (MUST BE BUILT)
--------------------------------

  Gap                            Effort    Notes
  ─────────────────────────────  ────────  ────────────────────────────────────
  Planner Agent                  High      LLM-driven DAG construction from
                                           KRA deltas. New LangGraph node.

FUNDAMENTAL CONSTRAINT: THE TOOL-FIRST INVARIANT
-------------------------------------------------
  Current rule: "LLM never fabricates findings — it only ranks detector output."
  Digital Worker rule: "LLM generates code and plans — but never executes
  directly on the host."

  These are compatible. The invariant shifts from "LLM is read-only on
  findings" to "LLM is write-only to sandbox workspace, never to host."
  The sandbox isolation layer enforces this boundary at the infrastructure
  level, the same way @detector_guard enforces it today for detectors.


REALISTIC EVOLUTION PATH
-------------------------

  Phase 1 (Current — DONE)
    Observation + Briefing pipeline. Covers the Observability Agent entirely.

  Phase 2 (Next)
    Add Analyzer Agent routing node. Add HITL Gate with Postgres state
    dehydration. Add FastAPI wrapper + Celery/Redis queue. No execution yet.

  Phase 3
    Add Planner + Generator agents. Sandbox container harness. Unit-test
    generated artifact syntax only (no live AWS execution in CI).

  Phase 4
    Add Executor + Validation agents. Loop A circuit breaker. Integration
    tests against synthetic Terraform env (the iac/synthetic_env/ already
    exists).

  Phase 5
    Loop B reconciliation. Reporter Agent. Full audit ledger UI. Eval harness
    extended to measure KRA resolution rate (target: ≥ 80% recall maintained).


VERDICT
-------
  The current Chandra architecture is NOT a digital worker as-is.
  It is a purpose-built READ-ONLY observation agent.

  However, it is the RIGHT foundation to evolve into one because:
  - The LangGraph graph is extensible (add nodes without rewriting the graph).
  - The Postgres + Pydantic discipline means new agent contracts slot in cleanly.
  - The detector suite is the exact discovery engine the Observability Agent needs.
  - The eval/CI infrastructure gives you regression safety as you add execution.

  The missing half is the WRITE side: Planner → Generator → Executor →
  Validation → HITL. That requires a sandbox, async job queue, and at minimum
  three new LangGraph agent nodes. Estimated effort: 8–12 engineering weeks
  for a production-grade implementation with proper isolation and circuit
  breakers.

SECTION 4: CAN A SINGLE AGENT ACHIEVE THE DIGITAL WORKER PLATFORM?
================================================================================

SHORT ANSWER
------------
Yes — a single agent CAN achieve the same outcomes, but it trades structural
safety for simplicity. Whether that trade-off is acceptable depends entirely
on your risk tolerance and operational scale.


WHAT "SINGLE AGENT" MEANS HERE
--------------------------------
A single LLM agent with a large context window and access to a tool belt:
  - observe()       → runs boto3 detectors
  - plan()          → reasons over findings and builds a task list
  - generate()      → writes .tf / .py / .sh files to workspace
  - execute()       → runs shell commands / terraform apply
  - validate()      → re-runs detectors post-execution
  - ask_human()     → pauses and emits a HITL prompt
  - report()        → produces the final audit markdown

The agent loops over these tools in a ReAct-style (Reason → Act → Observe)
cycle until all KRAs are satisfied or a circuit breaker fires.


WHAT A SINGLE AGENT CAN DO
---------------------------

  Capability                     Achievable?   Notes
  ─────────────────────────────  ────────────  ──────────────────────────────────
  AWS observation (5 KRAs)       ✅ Yes        Call existing detectors as tools.
  Risk assessment / routing      ✅ Yes        LLM reasons over findings inline.
  IaC / script generation        ✅ Yes        LLM writes files via tool call.
  Execution + stdout capture     ✅ Yes        execute() tool wraps subprocess.
  KRA validation post-execution  ✅ Yes        Re-call observe() tools after exec.
  HITL gate                      ✅ Yes        ask_human() tool pauses the loop.
  Self-healing on errors         ✅ Yes        Agent sees stderr, rewrites, retries.
  Audit report                   ✅ Yes        report() tool at end of loop.
  Circuit breaker                ✅ Yes        Retry counter tracked in agent state.


WHAT A SINGLE AGENT CANNOT DO WELL
------------------------------------

  Problem                        Why It Hurts
  ─────────────────────────────  ──────────────────────────────────────────────
  Context window blowout         A long run (observe + plan + generate + execute
                                 + validate + fix × 3) fills the context fast.
                                 The agent starts hallucinating or dropping
                                 earlier tool outputs as the window saturates.

  No structural safety boundary  In the multi-agent design, the Generator can
                                 ONLY write files — it has no execute tool.
                                 A single agent has all tools simultaneously.
                                 One bad reasoning step can jump straight from
                                 "generate" to "execute rm -rf" with no wall.

  Non-deterministic hand-offs    Multi-agent contracts (ExecutionDAG,
                                 ValidationMatrix) are typed Pydantic schemas —
                                 the hand-off is verified at parse time.
                                 A single agent's internal "decisions" are
                                 unverified natural language in the scratchpad.

  Async HITL is harder           Serializing a multi-agent graph to Postgres
                                 and resuming via webhook is clean. Serializing
                                 a single agent's entire reasoning chain +
                                 tool history mid-loop is fragile and vendor-
                                 dependent (requires checkpointing support).

  Parallel execution             Multi-agent: 5 KRA observers run concurrently
                                 via LangGraph Send(). Single agent: tools are
                                 called serially — observation takes 5× longer.

  Auditability                   Each agent in the multi-agent design produces
                                 a typed receipt (GeneratorReceipt, etc.) that
                                 is persisted independently. A single agent's
                                 audit trail is a raw tool-call log — harder to
                                 query, harder to present in a UI.

  Blast radius on failure        If the multi-agent Executor crashes, only that
                                 node's state is corrupt. A single agent crash
                                 mid-execution loses the entire reasoning chain
                                 and may leave infra in a partial-apply state.


SINGLE AGENT vs. MULTI-AGENT — DECISION MATRIX
------------------------------------------------

  Criterion                  Single Agent     Multi-Agent
  ─────────────────────────  ───────────────  ──────────────────────────────
  Build time                 Fast (weeks)     Slower (months)
  Operational simplicity     High             Medium
  Context safety             Low              High (scoped per agent)
  Structural guardrails      Soft (prompts)   Hard (typed schemas + tool walls)
  Parallel execution         No               Yes (LangGraph Send)
  Async HITL / dehydration   Fragile          Native (graph checkpointing)
  Auditability               Raw logs         Structured typed receipts
  Blast radius on failure    Full run lost    Isolated to one node
  Scale (10+ concurrent runs)Risky            Designed for it


RECOMMENDED SINGLE-AGENT ARCHITECTURE (IF CHOSEN)
--------------------------------------------------
If you choose the single-agent path, these guardrails are non-negotiable:

  1. Tool segmentation by phase
     Define separate tool groups and enforce in the system prompt that the
     agent may ONLY call execute-class tools after calling validate_plan()
     first. Soft wall — but better than nothing.

  2. Hard context budget
     Cap the agent loop at N tool calls (e.g., 30). If the budget is exceeded,
     force a report() call and escalate to HITL. Prevents runaway loops.

  3. Sandbox-first
     The execute() tool must run inside a Docker container regardless of
     agent architecture. This is the only hard safety boundary that cannot
     be prompt-engineered away.

  4. Structured tool outputs
     Every tool returns a Pydantic-validated JSON payload, not a raw string.
     This mimics the multi-agent contract discipline and gives you auditability
     even in a single-agent design.

  5. Checkpointing
     After each major phase (observe, plan, generate, execute, validate),
     persist the agent state snapshot to Postgres. If the agent crashes,
     resume from the last checkpoint — not from scratch.

  Diagram:

  [LLM Agent — ReAct Loop]
        │
        ├─ observe()     → DetectorContext → list[Finding]
        ├─ plan()        → findings → ExecutionDAG (JSON)
        ├─ ask_human()   → HITL pause → serialise to Postgres → webhook resume
        ├─ generate()    → DAG step → write file to /tmp/workspace/
        ├─ execute()     → file path → subprocess inside Docker → stdout/stderr
        ├─ validate()    → re-run observe() → ValidationMatrix (JSON)
        ├─ report()      → all receipts → FinalAuditReport (Markdown)
        └─ [loop until all_kras_satisfied=true OR retry_count >= 3]


VERDICT: SINGLE AGENT
----------------------
  A single agent IS capable of achieving the Digital Worker outcomes.
  It is the right choice for:
    • Proof-of-concept / MVP (fastest path to a working demo)
    • Low-concurrency deployments (1–2 runs at a time)
    • Teams without bandwidth for multi-agent orchestration engineering

  It is the WRONG choice for:
    • Production with concurrent runs across multiple AWS accounts
    • Compliance environments requiring hard audit trails per phase
    • Any scenario where a runaway LLM reasoning error could cause
      irreversible infrastructure damage at scale

  The pragmatic path: build the single-agent MVP first using the existing
  Chandra detector suite as the observe() tool belt. Validate the end-to-end
  loop works. Then harden into the multi-agent design by splitting the single
  agent's tool groups into bounded nodes — the refactor is mechanical once
  the tool contracts are proven.

  FULL FLOW DIAGRAM
  -----------------

  [Job submitted via FastAPI POST /jobs]
              │
              ▼
  ┌──────────────────────────────────────────────────────────────────────┐
  │                      AGENT LOOP (ReAct style)                        │
  │                                                                      │
  │  State: AgentState  ──  persisted to Postgres after each phase       │
  │  MAX_RETRIES = 3    ──  global circuit breaker                       │
  │                                                                      │
  │  Phase: OBSERVE                                                      │
  │  ┌────────────────────────────────────────────────┐                  │
  │  │  call observe(account_id, regions, kras)        │                  │
  │  │  → ObservabilityPayload saved to state          │                  │
  │  └──────────────────────────┬─────────────────────┘                  │
  │                             │                                        │
  │  Phase: ANALYZE                                                      │
  │  ┌────────────────────────────────────────────────┐                  │
  │  │  LLM reasons over ObservabilityPayload         │                  │
  │  │  Decision: risk_level = LOW | MEDIUM | HIGH    │                  │
  │  │  If HIGH or destructive actions present:       │                  │
  │  │    → call ask_human()                          │                  │
  │  │    → raise HITLPauseException                  │                  │
  │  │    → loop suspends, Celery task ends           │                  │
  │  │  If LOW/MEDIUM:                                │                  │
  │  │    → continue to PLAN                          │                  │
  │  └──────────────────────────┬─────────────────────┘                  │
  │                             │                                        │
  │  Phase: PLAN                                                         │
  │  ┌────────────────────────────────────────────────┐                  │
  │  │  call plan(jd_text, kras, observations)         │                  │
  │  │  → ExecutionDAG saved to state                 │                  │
  │  │  Lock any steps already marked complete        │                  │
  │  └──────────────────────────┬─────────────────────┘                  │
  │                             │                                        │
  │  Phase: GENERATE  (only for steps with generation_required=true)     │
  │  ┌────────────────────────────────────────────────┐                  │
  │  │  For each DAGStep needing generation:          │                  │
  │  │    call generate(step, workspace_path)          │                  │
  │  │    If GeneratorReceipt.status = FAIL:          │                  │
  │  │      retry (max 3), else → FAILED_AUTOMATION   │                  │
  │  └──────────────────────────┬─────────────────────┘                  │
  │                             │                                        │
  │  Phase: EXECUTE                                                      │
  │  ┌────────────────────────────────────────────────┐                  │
  │  │  For each DAGStep in dependency order:         │                  │
  │  │    call execute(artifact, command, workspace)   │                  │
  │  │    If exit_code != 0:   ◄── Loop A             │                  │
  │  │      pass stderr to generate() for patch       │                  │
  │  │      retry execute() (max 3)                   │                  │
  │  │      If still failing → FAILED_AUTOMATION      │                  │
  │  └──────────────────────────┬─────────────────────┘                  │
  │                             │                                        │
  │  Phase: VALIDATE                                                     │
  │  ┌────────────────────────────────────────────────┐                  │
  │  │  call validate(account_id, regions, kras, dag) │                  │
  │  │  If ValidationMatrix.all_kras_satisfied:       │                  │
  │  │    → continue to REPORT                        │                  │
  │  │  If unresolved_gaps present:   ◄── Loop B      │                  │
  │  │    increment retry_count                       │                  │
  │  │    If retry_count >= MAX_RETRIES:              │                  │
  │  │      → FAILED_AUTOMATION                       │                  │
  │  │    Else:                                       │                  │
  │  │      → back to PLAN (targeted sub-DAG)         │                  │
  │  └──────────────────────────┬─────────────────────┘                  │
  │                             │                                        │
  │  Phase: REPORT                                                       │
  │  ┌────────────────────────────────────────────────┐                  │
  │  │  call report(full AgentState)                  │                  │
  │  │  Persist FinalAuditReport to Postgres          │                  │
  │  │  phase = DONE                                  │                  │
  │  └──────────────────────────┬─────────────────────┘                  │
  │                             │                                        │
  └─────────────────────────────┼────────────────────────────────────────┘
                                ▼

                   GET /jobs/{job_id}/report

  Rules:
    - Write idempotent Terraform / Python / shell only.
    - Never write code that deletes resources unless the step explicitly
      contains action_type=delete.
    - If given a syntax error on retry, fix only the reported lines.
